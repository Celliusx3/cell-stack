### Refactor

**You own what the code does. The arrangement changes; the behaviour does not.** A bug or a missing feature found on the way is named in the reply and left for its own change, never folded in.

1. Apply the project's `CLAUDE.md` (already in context) as this repo's rules; open the rule files it links if the change touches them.
2. Read the code and every caller. List what the code promises (what it returns, saves, raises, and in what order) and which test checks each promise. Run those tests once and paste the command and the result. For a UI change the test is a rendered snapshot or a screenshot of every state, taken before and compared after; no baseline, no claim that it looks the same. Type check and lint do not count. A promise with no test is listed as the first test to write; it is not written yet.
3. Check the code against the rules before choosing the end state. Read the language page for each file type in scope first. Then take every name in scope (the folder, each file, class, function, parameter, field and constant) and every function body through each rule in the index, the language page and the project's own rules. List the names with a script (Python's `ast`, the TypeScript compiler's API), not from memory, so none is skipped, and give each a line: kept, or renamed to what, with the call site that reads it. Each finding is part of the change, or gets one line on why it stays: the project's own convention, a stored format, a caller outside scope. A strict reading not taken is the person's call at approval.
4. Say what the change makes better: what it lets you delete (a branch, an argument threaded through, a one-call wrapper, an impossible state), or what it makes clear (a name that says what it holds or returns, per **rule-name-for-the-reader**). A new model or class is added only where **rule-typed-boundaries** or **rule-group-by-subject** earns it. If the change only adds a layer, it is not worth doing; say so and stop.
5. Say the end state in plain words, with one example of the code after it lands, then how many files change.

**Plan mode stops here.** Steps 1 to 5 run during planning; the plan is steps 6 to 14.

6. More than about five files: the change is built by Build, not here. Run `${CLAUDE_PLUGIN_ROOT}/skills/cell-mode/procedures/spec.md`, then `${CLAUDE_PLUGIN_ROOT}/skills/cell-mode/procedures/tickets.md` with one ticket per piece; it ends at the person's approval. In plan mode the plan carries the spec and the tickets, approving the plan is that approval, and they are saved after it. Then run `playbooks/build.md` on the spec's folder, and this playbook ends here. When Build's cleanup runs this playbook, skip this step and make the edits here.
7. Write each missing test from step 2 and run it on the code as it is. It passes; paste the command and the result.
8. When the whole change is under about ten lines, make the edits in steps 9 and 10 yourself and say so in the reply. Otherwise hand them to one `general-purpose` subagent with the exact scope: the files, the names being moved, the promises that must hold, the language page for the file type.
9. Remove before you add: dead code, one-call wrappers (**rule-no-pass-through**), leftover references. Then the smallest change that reaches the end state (**rule-smallest-change**).
10. Move one thing, run the tests, move the next; whoever makes the edits runs them. Update every caller and delete the old name in the same move; never keep old and new side by side, except across tickets, where the old name stays until the last ticket deletes it. Grep each rename against strings, docs and tests.
11. Review the diff yourself and run the tests yourself. Paste the command and the result. Then take every name the diff adds or renames (a folder, a file, a class, a function, a parameter, a field, a constant, a test) through **rule-name-for-the-reader** again, at its call site; this runs on every refactor, unasked, and a name that fails is renamed before the commit.
12. Break it on purpose: for each moved piece, change one line so it is wrong and check that a test fails. A test that stays green was not watching; write one that does. Undo the break. Paste commands and results.
13. Easier to read? Fewer functions to keep track of, fewer branches, or one named type where loose values were passed around. Say which in one line. If none, undo the whole thing and say why.
14. Run `${CLAUDE_PLUGIN_ROOT}/skills/cell-mode/procedures/strip-comments.md` on the diff. Write the commits in order (removal, reshape, cleanup), each with its message. Make none unless asked; when asked, run `${CLAUDE_PLUGIN_ROOT}/skills/cell-mode/procedures/commit.md`.

**Reply:** what reads easier, first, and that nothing the person sees changes; what moved and what was deleted; the tests that guarded it and the proof (commands and results, including the break-on-purpose); what was undone; the commits proposed. When step 6 saves the change for Build, the reply at its stop is the spec's path, the ticket list with blockers, and the request to approve.
