### Fix

**You own the cause, not the symptom. The wrong behaviour goes away and nothing else changes.** A feature or a cleanup found on the way is named in the reply and left for its own change.

1. Apply the project's `CLAUDE.md` (already in context) as this repo's rules; open the rule files it links if the fix touches them.
2. Reproduce before reading code, on a scratch config, never the person's live state: point the config at a scratch directory, or undo what you wrote and say so. Keep the failure as evidence you can point at: a log line, a request and its reply, a command and its output. State the symptom in one line. A bug you cannot reproduce is not yet a bug; say what you tried.
3. Suspect state before code. Anything that fails after a restart, a deploy or a config change: check config files, caches, lock files, leftovers from a test. A setting that explains the symptom is named and fixed where it lives, with the person; it is never coded around. If the symptom is still there once it is fixed, go on to the code.
4. Trace the symptom to the line that causes it, then ask why that line is wrong. A plain mistake (a wrong operator, a line that adds twice) ends the search. A choice about what to do in some case is traced to where it was made. Grep for the same mistake elsewhere; each copy is fixed in this change, and anything else is named in the reply.
5. Decide the fix at the cause, never as a guard that hides the symptom (a nil check, a catch-all, a default). When the fix is a behaviour choice (what to do when X happens), run `/research` (`${CLAUDE_PLUGIN_ROOT}/skills/cell-mode/procedures/research.md`) on it. Put the fix where the project already keeps that kind of decision (a validator where data comes in, a policy module, a hook), and read one of the project's own examples first. A smaller diff that breaks a house rule is not a saving, per **rule-smallest-change**.
6. Say in one line why the fix is safe: the one thing that must stay true so it breaks nothing else. Name the regression test: where it goes, what it checks, and which reproduction from step 2 it turns into. Write nothing yet. When no cheap test exists, say why and name the closest check that runs (a script, a request, a log assertion); prefer no test over a test of mocks.

**Plan mode stops here.** Steps 1 to 6 only read and run; nothing on disk changes. The plan is the fix: the reproduction, the cause, the change, why it is safe, and the test. Steps 7 to 11 follow it.

7. Write the test and run it. It fails for the bug's reason, not another. Paste the command and the failure.
8. When the fix is under about ten lines, write it yourself and say so in the reply. Otherwise hand it to one `general-purpose` subagent with the exact scope: the files, the failing test, the project's `CLAUDE.md`, the language page for the file type. Review the diff: every line traces to the bug, per **rule-smallest-change**, and the test turns green.
9. Prove why the fix is safe by running code: a test or a script that calls the real thing and fails if the reason is false. When it cannot be run, say how far you got (pointed at the line, walked the case by hand) and that it is not proven.
10. Run the tests. Then show the original failure gone on the surface the person uses, on the scratch config from step 2, and paste what came out. A page is opened in a browser and clicked through, not checked with a request to the server: follow the repo's `drive-*` skill, or run `/drive` first when it has none. "Inconclusive" is not a pass. When a second fix fails the same check, stop: the two share a wrong assumption, so go back to step 4.
11. Run `/strip-comments` on the diff. Commits: the test and the fix as one story. Make none unless asked; when asked, run `/commit`. When the fix changes text a model follows (a prompt, a tool description), record it in the project's prompt ledger, per **rule-spell-the-call**.

**Reply:** what changes for the person, first; the cause in one line and the symptom it explained; the evidence (the test failing then passing, and the surface the person uses, each with its command and result); why the fix is safe and how far that was proven; anything found on the way and left for its own change; what the next engineer inherits.
