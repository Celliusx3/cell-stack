### Build

**Build a saved spec's tickets in order, then clean up, without stopping.** The input is a spec folder the Feature or Refactor playbook wrote, or one the person points at. Each ticket is committed as it passes; nothing is pushed or merged until the person asks. A bug found on the way is its own Fix, with its own test and commit.

1. Apply the project's `CLAUDE.md` (already in context) as this repo's rules; open the rule files it links if the change touches them.
2. Read the spec and every ticket in its folder. Build the `open` tickets in number order; a ticket whose blockers are not `done` waits. All of it goes on one branch for the feature, written where the mode says longer work goes.
3. For each ticket, write its Checks as one end-to-end check through the real entry point (a test, or the repo's how-to-use skill) and run it. It fails. Paste the command and the failure. A refactor ticket changes no behaviour, so nothing fails first: run the tests that guard its promises and paste them green instead, and after step 5 break each moved piece on purpose, check that a test fails, and undo the break.
4. Hand the ticket to one `general-purpose` subagent with the exact scope: the ticket file, the spec, the data shape, the check from step 3, the project's `CLAUDE.md`, the language page for the file type. You write any text a model will follow, per **rule-name-tools-exactly**. Review its diff for what it does; a name or a shape you would change goes on the rough-spots list.
5. Run the tests, then try the ticket on the surface the person uses, on a scratch config: follow the repo's `how-to-use-*` skill, or write one first with `${CLAUDE_PLUGIN_ROOT}/skills/cell-mode/procedures/write-how-to-use.md`. A bug that blocks the ticket is fixed now as its own Fix, with its own test. A failure the environment causes (a server setting, a model's window, a missing key) is named and fixed where it lives, with the person; it is never coded around.
6. Set the ticket's Status to `done` and commit the ticket with `${CLAUDE_PLUGIN_ROOT}/skills/cell-mode/procedures/commit.md`; the person's approval of the tickets covers this commit. Then start the next ticket, with no stop in between.
7. **Make it right.** Write the rough-spots list from your own review: a name that needs its docstring, two words for one thing, a function past the length cap, a promise with no test, anything shaped for one ticket rather than the codebase. Then run `playbooks/refactor.md` with the feature's whole diff as the scope and the list as the candidates, straight away. It writes a test for every promise that has none before anything moves. Refactor's hand-off to Build is skipped here: its edits are made inside this Build, never in a second one.
8. **Make it clean.** Run `${CLAUDE_PLUGIN_ROOT}/skills/cell-mode/procedures/strip-comments.md` on the whole diff. Check every ticket's Checks and the spec's "How we will know it works" against the final code, and fix what fails. Update the docs the change made wrong: the project's plan, its prompt ledger, a how-to-use skill's feature map. Run the tests and try it once more on the final code, and paste both.
9. Commit the cleanup with `${CLAUDE_PLUGIN_ROOT}/skills/cell-mode/procedures/commit.md` as the last commit. Push, merge or open a PR only when asked.

**Reply:** what changes for the person, as numbered steps they can try (for a refactor: that nothing they see changes, and what reads easier); per ticket, its check red then green (a refactor ticket: green before and after, and its break), what trying it showed, and its commit; each finding and what fixed it; what the refactor moved and the break-on-purpose results; the final run; what the next engineer inherits; the decisions left open.
