### Build

**Build a saved spec's tickets in order, then clean up, without stopping.** The input is a spec folder the Feature playbook wrote, or one the person points at. Each ticket is committed as it passes; nothing is pushed or merged until the person asks. A bug found on the way is its own Fix, with its own test and commit.

1. Apply the project's `CLAUDE.md` (already in context) as this repo's rules; open the rule files it links if the change touches them.
2. Read the spec and every ticket in its folder. Build the `open` tickets in number order; a ticket whose blockers are not `done` waits. All of it goes on one branch for the feature, written where the mode says longer work goes.
3. For each ticket, write its Checks as one end-to-end check through the real entry point (a test, or the repo's drive script) and run it. It fails. Paste the command and the failure.
4. Hand the ticket to one `general-purpose` subagent with the exact scope: the ticket file, the spec, the data shape, the failing check, the project's `CLAUDE.md`, the language page for the file type. You write any text a model will follow, per **rule-spell-the-call**. Review its diff for what it does; a name or a shape you would change goes on the rough-spots list.
5. Run the tests, then drive the ticket on the surface the person uses, on a scratch config: follow the repo's `drive-*` skill, or run `/drive` first. A bug that blocks the ticket is fixed now as its own Fix, with its own test. A failure the environment causes (a server setting, a model's window, a missing key) is named and fixed where it lives, with the person; it is never coded around.
6. Set the ticket's Status to `done` and commit the ticket with `/commit`; the person's approval at stop 2 covers this commit. Then start the next ticket, with no stop in between.
7. **Make it right.** Write the rough-spots list from your own review: a name that needs its docstring, two words for one thing, a function past the length cap, a promise with no test, anything shaped for one ticket rather than the codebase. Then run `playbooks/refactor.md` with the feature's whole diff as the scope and the list as the candidates, straight away. Its step 2 writes a test for every promise before anything moves.
8. **Make it clean.** Run `/strip-comments` on the whole diff. Check every ticket's Checks and the spec's "How we will know it works" against the final code, and fix what fails. Update the docs the change made wrong: the project's plan, its prompt ledger, a drive skill's feature map. Run the tests and the drive once more on the final code, and paste both.
9. Commit the cleanup with `/commit` as the last commit. Push, merge or open a PR only when asked.

**Reply:** what changes for the person, as numbered steps they can try; per ticket, its check red then green, what the drive showed, and its commit; each finding and what fixed it; what the refactor moved and the break-on-purpose results; the final run; what the next engineer inherits; the decisions left open.
